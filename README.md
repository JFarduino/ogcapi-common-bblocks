# OGC API - Common Building Blocks

[OGC API - Common](https://ogcapi.ogc.org/common/) as [OGC Building Blocks](https://ogcincubator.github.io/bblocks-docs/):
the reusable schemas and OpenAPI components, together with the requirements classes, clauses and
annexes from which the standards documents are generated. The register currently holds
[Part 1: Core](https://docs.ogc.org/is/19-072/19-072.html) (OGC 19-072, version 1.0.0); further parts
go next to it (see [Adding a part](#adding-a-part)).

This repository merges two former repositories into a single register, with their full Git history:

| Former repository | Content now in this repository |
| --- | --- |
| [ogcincubator/bblocks-ogcapi-common](https://github.com/ogcincubator/bblocks-ogcapi-common) | Part 1 API components: `api`, `schemas/`, `paths/`, `responses/` |
| [JFarduino/ogcapi-common-standards-as-bblocks](https://github.com/JFarduino/ogcapi-common-standards-as-bblocks) | Part 1 document: `preface/`, `clauses/`, `requirements/`, `annexes/`, `test-resources/`; `standards.yaml` |

## Contents

| Part | Sources | Namespace | API blocks | Document blocks |
| --- | --- | --- | ---: | ---: |
| [Part 1: Core 1.0, OGC 19-072](https://docs.ogc.org/is/19-072/19-072.html) | [_sources/part1](_sources/part1) | `ogc.api.common.part1.*` | 15 | 25 |

*API blocks* are the schemas and OpenAPI components (`api`, `schemas/`, `paths/`, `responses/`).
*Document blocks* are the `preface/`, `clauses/`, `requirements/` and `annexes/` blocks that make up
the standards document.

The identifiers are those of the two former registers, unchanged (e.g. `ogc.api.common.part1.schemas.link`,
`ogc.api.common.part1.requirements.core`). The requirements classes, which used to import the API
components from the `@ogc/ogcapi-common` register, now depend on them locally, and the register imports
nothing (`imports: []`): OGC Main imports `@ogc/ogcapi-common`, so importing OGC Main back would create a
circular dependency.

## Standards documents

[standards.yaml](standards.yaml) defines the documents generated by the
[bblocks-specgen](https://github.com/JFarduino/bblocks-specgen) build plugin declared in
[bblocks-config.yaml](bblocks-config.yaml):

| Id | Document | Source blocks |
| --- | --- | --- |
| `part1` | OGC API - Common - Part 1: Core 1.0 (OGC 19-072) | `ogc.api.common.part1.*` |

The plugin is installed from the `feature/update` branch of
[JFarduino/bblocks-specgen](https://github.com/JFarduino/bblocks-specgen), a fork of
[ogcincubator/bblocks-specgen](https://github.com/ogcincubator/bblocks-specgen) that adds the `layout: ogc`
rendering (ModSpec tables, numbered subclauses, OGC cover) and file includes. The documents are written
to `build/standards/<id>/index.html`.

### How OGC 19-072 maps to the generated document

The document is rendered with `layout: ogc` and has the structure and numbering of OGC 19-072: preface
I-VI, clauses 1-12, Annex A (Abstract Test Suite), Annexes B-F and the Bibliography.

- **Clauses.** Clause 10 "Encoding Requirements Classes" is a block of its own (10.1 Overview) with the
  HTML and JSON requirements classes as subclauses 10.2 and 10.3 (`subclauses` in `standards.yaml`).
  Headings in `description.md` carry no number: the layout numbers them, and cross-references use the
  `#sec-<number>` anchors (e.g. `[Clause 8.2](#sec-8.2)`).
- **Statements.** Requirements (with their parts A, B…) and recommendations are in the
  `requirements.yaml` of their class (`type: recommendation`), and are placed in the text with
  `<!-- requirement: <id> -->` / `<!-- recommendation: <id> -->` markers, where OGC 19-072 has them
  (Recommendation 1 of the Core class is placed in clause 6.3). They are numbered in document order:
  Requirements 1-27, Recommendations 1-18. The recommendations that OGC 19-072 identifies as `/per/...`
  carry an explicit `uri`.
- **Annex A.** The conformance classes and abstract tests A.1-A.27 are defined in each
  `requirements.yaml` (`conformance-class`, `abstract-tests`); the `annexes/ats` block lays out the annex
  with `<!-- conformance-class -->` and `<!-- abstract-test -->` markers. `tests.yaml` lists the test
  resources that bblocks-postprocess validates against the schema of the class; abstract tests refer to
  them with `tested-by`.
- **Schemas.** The schemas that OGC 19-072 includes (link, landingPage, confClasses) are not copied:
  they are code blocks with an `include=` option, filled at build time from the API blocks of this
  register and followed by a link to the building block that defines them, e.g.
  ````markdown
  ```yaml include=bblocks://ogc.api.common.part1.schemas.link
  ```
  ````
- **Front and back matter.** The cover carries the notices of the published document
  (`boilerplate.notices`); the informative references are in the closing, unnumbered Bibliography.

Known differences with the published document: Annex A is titled "Annex A (normative) Abstract Test
Suite" (OGC 19-072 has "(informative) … (Normative)"), and in Recommendation 4 the "Statement" row comes
before part A instead of after it.

## Adding a part

A further part of OGC API - Common (e.g. Part 2: Geospatial Data, OGC 20-024, draft) goes in its own
directory, with its own namespace segment and document entry:

1. API and document blocks under `_sources/part2/` (identifiers `ogc.api.common.part2.*`), with the
   same subdirectories as Part 1;
2. a second entry in the `standards` list of [standards.yaml](standards.yaml) (`id: part2`,
   `prefix: ogc.api.common.part2`, `class-id-prefix: ogc.api.common.part2.requirements.`), generated
   to `build/standards/part2/index.html`;
3. a row in the [Contents](#contents) and [Standards documents](#standards-documents) tables above.

Part 2 blocks can depend on Part 1 blocks directly (`ogc.api.common.part1.*`), without any import.

## Build and view locally

Requires Docker. The postprocessor image is only published for `linux/amd64`: on Apple Silicon, set
`DOCKER_DEFAULT_PLATFORM=linux/amd64` (Docker Desktop emulates it).

```shell
# Build (validation, register, documentation and the standards document)
DOCKER_DEFAULT_PLATFORM=linux/amd64 ./build.sh

# Generated standards document
open build/standards/part1/index.html

# Optional: browse the Building Blocks (and the document) in the viewer at http://localhost:9090
./view.sh
```

From a terminal, the first build (and the first one after the `pip:` line of the plugin changes) asks
for permission to install the `bblocks-specgen` plugin. In scripts/CI, pass `--skip-permissions true` to
`./build.sh` instead. Set `BBP_IMAGE_TAG` to pin a postprocessor image.

The plugin is installed from GitHub (`feature/update`), so changes to bblocks-specgen are picked up once
pushed to that branch. To try a local clone first, put it in `bblocks-specgen-jules/` (ignored by git)
and use `bblocks-specgen @ file:///workspace/bblocks-specgen-jules` as the `pip:` entry in
`bblocks-config.yaml` (`build.sh` mounts the repository on `/workspace`); GitHub workflows cannot see
that folder.

Outputs:

- `build/standards/part1/index.html` — the generated OGC 19-072 document (`report.json` next to it lists
  how each Building Block was used);
- `build-local/` — register, documentation, annotated schemas and validation reports (local builds only).

## Publication

On every push to `main`, [process-bblocks.yml](.github/workflows/process-bblocks.yml) validates the
blocks, generates the documents, commits `build/` and publishes to GitHub Pages (the template's
mechanism is unchanged, see [USAGE.md](USAGE.md)); the repository's Pages source must be set to
"GitHub Actions". Pull requests are checked read-only by
[pr-check.yml](.github/workflows/pr-check.yml).

Once published, the site has the Building Blocks viewer at its root and the standards document under
`build/standards/part1/`, and the register is available at
<https://jfarduino.github.io/ogcapi-common-bblocks/build/register.json>.
